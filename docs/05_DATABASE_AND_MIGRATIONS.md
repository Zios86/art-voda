# База данных и миграции

## Правила

- Кодировка `utf8mb4`.
- Все значения передаются параметрами prepared statements.
- Внешние ключи и индексы добавляются осознанно.
- Несколько связанных записей меняются в транзакции.
- Миграция должна быть повторно безопасной либо явно проверять версию схемы.
- Перед миграцией рабочей базы создаётся backup базы и фотографий.

## Чистая установка

1. Создать пустую БД `kioskvody`.
2. Импортировать `private/schema.sql`.
3. Не запускать исторические миграции, уже включённые в текущую schema.
4. Создать конфигурацию из example-файла.
5. Проверить таблицы и вход администратора.

## Обновление старой установки

1. Определить версию базы.
2. Сделать backup.
3. Прочитать миграцию и проверить ожидаемое исходное состояние.
4. Запустить миграции строго по порядку, например v15 → v16. Для текущего v18 после v16 выполнить `private/migrate_v18_audit.sql`.
5. Проверить количество строк, ограничения и журнал.
6. Только затем обновлять PHP-файлы.

## Импорт CSV

Этап 1 — парсинг и отчёт: новые, изменённые, ошибочные, повторяющиеся строки. Этап 2 — отдельное подтверждение, повторный пароль, backup, транзакция, история и аудит. Путь фотографии допустим только для существующего безопасного файла.

## Резервные копии

Кнопка полной копии создаёт ZIP с JSON базы, используемыми изображениями и SHA-256 в `manifest.json`. Автоматические страховочные JSON-копии хранятся отдельно и удаляются по настоящему времени файла. Скачанный ZIP всё равно нужно хранить вне Timeweb.

## Аудит v18

`kiosk_audit.kiosk_id` допускает `NULL` для общего события всей операции, а `action` расширено до 40 символов. Импорт и восстановление записывают действия по каждой затронутой точке и завершающее системное событие. На существующей базе это включает миграция `migrate_v18_audit.sql`.
