# Архитектура

## Общая схема

```text
Браузер
  ├─ публичные PHP-страницы
  ├─ CSS/JavaScript/PWA
  ├─ API списка автоматов
  └─ /admin
        ├─ сессия и авторизация
        ├─ CSRF и повторный пароль
        ├─ CRUD/пакетные операции
        ├─ импорт CSV и фото
        └─ backup/аудит/диагностика
                │
                ▼
              MySQL

private/
  ├─ конфигурация и общие серверные функции
  ├─ schema.sql и миграции
  └─ runtime/backup/logs (уточнить фактические пути)
```

## Границы публикации

Document root должен указывать на `public_html`. Каталог `private` не должен отдаваться веб-сервером. Релиз собирается по белому списку; лишние рабочие, старые и внутренние файлы не попадают в ZIP.

## Поток публичных данных

Ожидаемый поток: MySQL → API → JavaScript карты/списка. `data/kiosks.json` может использоваться как аварийный или офлайн-источник. Если он остаётся, обновление должно происходить после успешной транзакции изменения базы, иначе посетители получают старые данные.

## Поток административного изменения

```text
Форма → авторизация → CSRF → валидация → backup при опасной операции
→ транзакция → запись версии/аудита → обновление производного JSON
→ commit → ответ → обновление интерфейса
```

При ошибке выполняется rollback; браузерный черновик нельзя удалять до подтверждённого успеха.

## PWA и кеш

Service Worker не должен кешировать админку, приватные ответы или персональные данные. Версии ресурсов в `sw.js`, HTML и URL должны совпадать. После изменения кешируемого CSS/JS меняется версия кеша и проверяется офлайн-режим.
